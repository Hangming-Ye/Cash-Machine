# 记忆方案补充调研：从记录到可用经验

2026-09-20。官方文档与项目资料核实，未安装或进行 Grok 实测。本文取代研究 07 中“先做账本、数个季度后再考虑记忆组件”的实施建议；研究 07 其余内容仍仅为候选。

## 现有方案比较

| 方案与官方来源 | 已有机制 | 本项目可借鉴／复用 | 限制与判断 |
| --- | --- | --- | --- |
| [LangMem](https://github.com/langchain-ai/langmem/blob/main/docs/docs/concepts/conceptual_guide.md) | 接收新材料和已有记忆，提取、更新与整合；区分知识、案例和行为方法记忆 | 借鉴提炼与合并方法；评估其记忆管理组件，而非引入整个任务编排框架 | 需要专门定义投研经验内容；原生框架集成不是现有 Grok 环境可直接复用的证明 |
| [Mem0](https://github.com/mem0ai/mem0)；[提取行为](https://github.com/mem0ai/mem0/blob/main/docs/core-concepts/memory-operations/add.mdx) | 提供记忆添加、提取、检索等能力，有库、自托管服务、云平台及 CLI／技能入口 | 作为现成组件候选，测试可否完成去重更新、带出处召回和注入 | 不能把原始写入当作经验沉淀；不同部署版本能力需分别核实；仍需调用方把结果送给专员 |

## 当前取舍（研究建议，未锁定实现）

结合本轮 Grok 产品入口和组件源码调研，优先验证“提取 LangMem／Letta 方法，使用少量经验文档”的路径。Mem0 保留为检索能力不足时的组件备选；外部记忆服务不会自动解决原生 Bot 的任务注入。不能在 Grok 调用、模型兼容和效果未验证前声称可直接使用。不引入新的编排框架、图数据库或自我进化审批流程作为先决条件。

最低有效过程：研究记录及复盘 → 提炼有条件的经验 → 合并重复并压缩 → 新任务按问题检索 → 在明确上下文预算内实际注入 → 研究使用及反证回写。原始记录用于追溯，压缩经验用于工作；二者职责不同，不要求物理分库。

每条经验至少说明教训或检查项、适用条件、案例出处、反例／局限和有效时间。经验只能提示研究检查，不能自行改写任务权限或变成已验证因子。注入应包含相关的反方经验，不能仅累积支持既有观点的材料。

考虑到目标模型能力，初版由 Skill 明确安排任务前读取与任务后整理；必要的小程序检查筛选字段、材料长度及引用是否存在，模型按固定方法提炼和判断。程序不能仅凭格式校验判断一个自然语言结论是否失真；仍需证据核对和效果测试。该建议不要求新增调度状态机，也不依赖模型自己想起“去读记忆”。

## 选型验证与规格关系

用相同历史材料比较两条轻量路径：材料包括重复教训、相互矛盾结论、已失效事实及无关内容。观察压缩前后长度、关键信息保留、召回相关性、失效项处理、实际注入内容、研究是否补上曾遗漏的检查，以及调用次数与维护负担。不以供应商通用 benchmark 代替本场景验证。

优先使用虚构或脱敏样例。此轮只做资料调研，没有向外部记忆服务发送账户、持仓或凭证，也没有安装新依赖。

spec001 的 FR-021、US6、SC-007 已要求上述闭环；具体组件和预算由 plan 通过小样例选择。验收必须看到新会话实际收到并使用相关经验，不能仅证明文件存在或检索接口可调用。

## 按任务特点组织记忆（用户反馈补充）

定时、长期和重分析是可叠加的工作特点。例如每周跟踪一个产业链主题，同时涉及三者。以下是设计建议；“重分析”按分析密集任务理解，同时覆盖同一问题重新分析的复用与失效处理。它们共享一套记忆能力，通过明确的任务方法决定输入与更新，不增加分类状态机。

| 任务特点 | 保存什么 | 如何沉淀压缩 | 何时、注入什么 | 应证明的效果 |
| --- | --- | --- | --- | --- |
| 定时：持仓巡检、事件跟踪 | 上次有效基线、已处理事件、未解决问题、数据时点 | 比较本次与上次，仅合并有意义变化；无变化不重复生成教训 | 每次调用带入基线、待验证项及新证据；行情重新获取 | 能指出变化和未变化，不把反复出现的信息当作新证据，不让重复报告挤满记忆 |
| 长期：产业主题、公司论点、因子假设 | 目标、当前假设、支持与反证、关键转折、失败路径、下一验证点 | 围绕研究主题维护当前摘要，保留关键演变和出处；阶段复盘后提炼有条件经验 | 续研时注入当前研究摘要、未决问题及相关经验，细节按需回查 | 新会话能接续研究、不重新从头发现；保留被否定的路径及未解决分歧 |
| 重分析：供应链深挖、估值、因子验证 | 原始证据定位、可复查的分析理由、假设、计算口径、阶段结果及反证 | 阶段摘要保留结论成立条件与不确定性，计算结果保留输入依据；可复用方法和本次事实分开 | 分析前按子问题注入相关材料及经验；证据或假设变化时回查并重算／重评 | 压缩不造成推断升级为事实；能解释结论并复核关键计算，不因旧摘要锚定错误答案 |

共同原则：原始材料可追溯，工作摘要可更新，跨任务经验带适用条件。三者是内容用途，不要求三个数据库。任务上下文优先保留当前问题所需内容，不把全部历史无差别塞入提示词。一般性经验只提示研究检查，不替代当前数据或统计验证。

现有组件的评估也按这三类样例展开：能否比较增量、持续合并主题摘要、按分析问题找回依据，并把适量内容实际送给专员；仅支持 add/search 不足以证明满足要求。采用现成组件还是提取其方法，应由这些效果及维护成本决定。

## 组件源码下钻与复用结论

本轮由独立子 agent 阅读官方源码／文档；未安装、未运行。以下路径固定的是本轮查阅位置，不是锁定依赖版本，实施选型仍须记录具体版本。

| 组件 | 具体实现入口与观察 | 能直接复用什么 | 更适合提取的方法／不可外推的能力 |
| --- | --- | --- | --- |
| Mem0 | [memory/main.py](https://github.com/mem0ai/mem0/blob/main/mem0/memory/main.py)、[prompts.py](https://github.com/mem0ai/mem0/blob/main/mem0/configs/prompts.py)：结合相近已有记忆与新材料，模型提出新增／更新／删除／不变，程序执行存储动作。[CLI](https://github.com/mem0ai/mem0/blob/main/cli/README.md)提供 shell 调用，面向 Platform | CLI 检索／写入可作为候选；OSS 库另需模型、embedding 和存储配置 | 默认事实／偏好抽取不等于投研经验：需补出处、反证、条件与时效。服务输出必须再通过任务输入交给 Bot；不替换 Bot 内部记忆 |
| LangMem | [knowledge/extraction.py](https://github.com/langchain-ai/langmem/blob/main/src/langmem/knowledge/extraction.py)：新材料与 existing memory 合并、去重压缩；[Memory API](https://langchain-ai.github.io/langmem/reference/memory/)提供结构化 manager；[依赖](https://github.com/langchain-ai/langmem/blob/main/pyproject.toml)引入 LangChain／LangGraph 等 | manager 可在自有调用代码中使用，不要求全部迁移 agent；但仍需库依赖及独立模型调用 | 优先提取“已有摘要 + 本轮材料 → 保留／更新／合并”的方法和经验字段，不默认引入后台 executor 或整个框架；示例中的 system prompt 拼接不适用于直接控制 Bot |
| Letta | [MemFS](https://github.com/letta-ai/letta-docs-md/blob/main/concepts/memfs/index.md)、[记忆整理](https://github.com/letta-ai/letta-docs-md/blob/main/configuration/memory/index.md)、[运行指令](https://github.com/letta-ai/letta-code/blob/main/src/agent/prompts/letta.md)：精简常驻内容、按需文件、版本历史及后台整理 | 本轮不把完整 Letta 作为现成 Bot 记忆插件 | 借索引、主题文件、按需读和去重整理；Letta 自身的 prompt 编译／自动注入依赖其运行环境，Grok Bot 不继承这些保证 |

因此先复用方法，保留接入组件的空间。文件方案也不是“只存文件”：必须明确提炼、合并、相关读取和实际使用；如果小样例证明其召回或整理达不到需求，再引入能解决该具体缺口的组件。

与产品入口结合的完整判断见 [研究 15](15-grok-memory-integration.md)。现有方案中依赖原生 hooks 的能力仅用于比较，不写成 Grok Bot 已有功能。
