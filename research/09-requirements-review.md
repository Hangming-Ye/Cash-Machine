# 用户目标与调研完整性独立审查

审查日期：2026-09-20。范围仅为主体架构 v0.2、调研索引、供应链 Skill、WorkBuddy 本机检查和金融 Agent 应用调研。本审查判断这些材料是否足以指导下一步建设，不复核外部项目的所有事实，也不改写主体方案。

## 总体判断

材料已经覆盖用户的三个投资目标、Grok Bot 的弱模型现实、24/7 与多 Bot 产品边界、客观与主观信息、判断台账，以及大量 Skill / MCP / CLI / Agent 候选。它不是“少调研了几个项目”的问题。

当前主要缺口是从广泛调研到可交付系统之间仍有一层没有收口：不少对象仍停留在“候选、待核验、按缺口试验”，Chief 的规划与并发仍是原则，手机卡仍是展示示例，WorkBuddy 也尚未形成可复现的组件提取清单。若直接按现有阶段推进，团队可能先做很多 schema、证据门和异常用例，却较晚才验证用户每天是否真的得到更好的研究和决策。

以下六项应作为主体架构定稿前的必要修正；它们都直接对应用户的发现机会、单票辅助、持仓判断、Chief 规划或手机使用目标。

## 必须修正 1：供应链研究改成“线索快车道 + 投资深研”两速制

主体流程把瓶颈、利润捕获和估值三关写得很完整，但容易把“早期潜在公司发现”做成“等收入证实后才进入候选”。供应链专题甚至写成三关都通过才进入优先研究/候选买入阶段。这个门槛适合形成投资观点，却不适合 Serenity 类目标中的早期发现。

应明确两种产物：

- **早期线索卡**：允许收入尚未确认，但必须给出成熟度阶段（研发/送样/认证/量产/订单/收入）、领先指标、下一可证实事件、概率区间和最大风险；只进入发现池，不给买入结论。
- **可投资研究卡**：通过公司暴露、利润桥和估值三关后，才进入买入区间、持有或淘汰判断。

这样既保留证据纪律，又不会错过用户要求的 prospective company。首个验收主题应要求同时产出一个早期线索、一个可投资候选和一个被否定案例，而不只是调查 2–3 家公司。

依据：主体架构 122–131 行；供应链调研 139–184 行。现有材料已经具备成熟度、前置信号和 thesis diff 字段，缺的是产品状态与输出分流。

## 必须修正 2：把 Chief 从角色说明落成可执行的规划与并发协议

“五类问题、三条队列、60/25/15”说明了思路，但还不能约束弱模型如何把一个主题拆成任务、如何并发、何时停止、失败后如何改路。六个职责如果只靠自然语言，Chief 仍可能重复搜索、让多个 Bot 读同一批新闻，或在缺一项数据时卡住整条链。

需要一份机器可读的 `research_plan`，每个节点至少包含：决策问题、依赖、owner、输入版本、来源类型、输出 schema、验收条件、预算、截止时间、停止条件、替代路径和是否可并行。Chief 只能执行以下动作：选模板、展开依赖图、分配可并行节点、核对回执、重试/降级、合并分歧、生成用户待决策项。

首版并发拓扑也应写死：数据更新单写者；同一标的基本面、事件/舆情、因子计算可并行；估值依赖基本面快照；风险复核依赖前三者；最终卡片只由 Chief 发布。每个主题限制并发数和重复来源预算，失败节点不阻塞无依赖节点。

验收应使用一个真实主题，证明 Chief 能并发派发、收到结构化回执、发现缺口后换源或降级，并在手机端说明“已完成什么、仍缺什么、下一步为何最值”。

依据：主体架构 78–99、115–118 行；Agent 应用调研的固定状态机、预算和 Artifact 建议。现有原则正确，欠缺可执行契约。

## 必须修正 3：为三个目标各选定一套首版信息源组合和综合算法

主体架构已为美股列出较明确的官方源基线，也覆盖电话会、机构观点、新闻和社交；但 A/H 股研究源仍把多个供应商合并为一行“选一个试验”，三个目标各自依赖的最小来源组合也没有形成可执行配置。这不足以支持 build / buy / reuse 决策，也无法估算第一条闭环何时能跑通。

应立即冻结一个最小来源组合，而不是继续横向扩表：

| 目标 | 首版必须覆盖 | 综合输出 |
|---|---|---|
| 供应链 | 官方披露/交易所 + 行情估值 + 一个关系或产业内容源 | 关系边、成熟度、瓶颈证据、利润桥、计价 |
| 单票因子 | 可复权价格量 + 公司行动 + 事件日历；基本面文本后置 | 当前信号、历史分位、适用期限、样本外增量、失效状态 |
| 持仓/自选 | 只读账户 + 行情 + 公告/电话会 + 新闻 + 一路社交/机构观点 | 自上次判断的变化、分歧、买/卖/观望、理想价格区间 |

主观材料的综合算法还应具体化：相同事件聚类；事实可信度、观点方向、市场传播强度三列分开；投行观点保留作者、发布日期、目标期和假设；社交只反映叙事/线索；最终卡片显示“事实变化、预期变化、价格变化”各自来自哪里。主体数据模型已有字段，需把它变成固定产物。

每个新源用同一试验集比较覆盖、全文/摘要、时点、引用定位、延迟、成本、授权和 24/7 可用性。一个缺口只选一个胜者和一个备用者；未胜出的候选停止继续集成。

依据：主体架构 168–184 行；调研索引 28–50 行。调研广度足够，当前需要收敛而不是再增加名单。

## 必须修正 4：WorkBuddy 结果要形成“可复现实装清单”，不能停在静态阅读

本机检查真实确认了 WorkBuddy v5.3.8、已安装目录和市场缓存，也读到了若干脚本与 Prompt/Skill 文档。这已经纠正了“只看市场宣传”的问题，但仍未满足“实际安装/源码 Prompt 提取后可落地复用”的最终目的：缓存、已安装、已授权和可运行仍混在多份文字说明里，且没有组件级提取物。

应为每个准备复用的 WorkBuddy 对象生成一张 manifest：installed/cache 状态、版本或内容 hash、实际入口、Prompt/Skill 文件、脚本入口、输入输出、依赖、凭证来源、运行位置、许可、要抽取的具体模板/函数、明确不抽取部分、一次只读 smoke test 和结果。至少完成以下三个：`market-news-analyst`、`stock-analysis`、一个中国研究内容连接器。

Prompt 提取必须产出字段级映射，例如“事件分类 → 自有 `event_cluster` schema”“观点/证据要求 → `claim` schema”，不能只写“抽取框架”。宿主临时 token、硬编码路径和服务端能力不进入提取包。

只有通过 smoke test 的服务才可标成 `reuse`；只有代码/模板可用的标成 `adapt`；只能借鉴思路的标成 `rebuild`；其余标成 `defer`。这会把当前采用表变成真正的 build / buy / reuse 决策。

依据：WorkBuddy 检查 7–35 行；调研索引 53–57 行。当前证据支持静态审阅完成，不支持运行能力完成。

## 必须修正 5：手机端必须是决策收件箱，不只是报告卡片

现有手机卡包含结论、价格、买入条件和持仓快照，但没有定义用户在几分钟内如何处理多个 Bot 的结果。24/7 系统的首要界面应是按优先级排序的“注意事项收件箱”。

每张卡首屏只显示：对象、相对上次的新变化、建议动作、理想价格区间、时效、置信/缺口、下一事件。用户应能直接选择 `接受并记录 / 加入观察 / 暂缓至事件 / 要求补证 / 驳回理由`，并能点开证据、分歧和完整研究包。批量操作只用于“无变化”和低风险观察项；买卖观点逐项确认。

还需定义四种系统卡：研究完成、等待用户、数据/登录故障、预算/配额耗尽。推送只在观点、价格区间、失效条件、组合风险或任务阻塞发生实质变化时出现。每次操作回写判断台账，保存“系统建议”和“用户决定”两条记录。

P1 验收除了连续五日运行，还应要求用户用手机完成一次补证、一次加入观察、一次改判查看和一次故障恢复；否则只能证明后台产出，不能证明移动端工作台可用。

依据：主体架构 147–166、196–225 行。现有通知原则合理，交互闭环尚未定义。

## 必须修正 6：单票因子产物要直接服务主观交易，而不是只交实验报告

单票因子方法对 PIT、滚动验证、成本和失败实验处理得好，但首批约 12 个因子仍是数量目标，且最终如何进入每天的买/卖/观望判断不够具体。

首版应从三类主观决策各选 1–2 个因子：趋势确认、回撤/波动风险、事件后等待。每个因子卡固定显示：决策用途、计算定义、预测期限、当前值和历史分位、样本外相对基线增量、交易成本敏感性、适用市场状态、失效状态、最近更新时间。多个因子不强行合成一个黑箱分数；若冲突，手机卡直接保留分歧。

验收对象不是“Sharpe 更高”，而是回答一个具体问题，例如“该标的财报跳空后等待几日是否比立即追涨改善回撤/收益分布”。没有稳定增量同样结案，并记录以后什么新样本才值得重开。

依据：主体架构 135–145 行；Agent 应用调研的因子证据包和确定性计算边界。

## 可以后置

- 专用图数据库、全量向量库、复杂记忆衰减、多 Agent 辩论和自动因子搜索；SQLite/Parquet 与不可变台账足够验证首版。
- Panjiva、FactSet 等昂贵供应链数据库；先用一个真实主题证明公开披露与较便宜来源的缺口，再采购。
- 独立心跳服务、跨区域高可用和 live broker；先完成 Grok Bot Routine 的漏跑检测与只读闭环，人工下单保持不变。
- 约 30 个完整异常案例不应挡住 P1。首轮保留 8–10 个高概率、高损失案例；在三条真实闭环跑通后扩充回归集。
- 新的 Agent 编排平台、永久行业角色和更多市场插件；现有调研已经说明这些不会自动改善 Chief 的规划或投资研究质量。

## 建议的下一轮唯一验收包

用一个用户真实持仓、一个真实自选标的和一个真实供应链主题，连续运行五个交易日。交付物必须同时包含：Chief 的可执行计划与并发回执、客观/主观来源综合、一个早期供应链线索和一个被否定候选、三类单票因子中的至少一类、手机决策操作记录、WorkBuddy 三组件 manifest，以及原始建议和用户决定分离的判断台账。

这套验收包能同时回答三个最重要的问题：Grok Bot 弱模型能否可靠协调；现有 Skill / MCP / CLI 到底哪些值得复用；系统是否真正改善了用户发现机会、判断单票和管理持仓的过程。通过后再扩大数据源、标的数和异常测试范围。
