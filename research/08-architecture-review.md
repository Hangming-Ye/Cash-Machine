# 初步架构独立审查：可行，但需缩小 Agent 层并补上确定性核心

审查范围：`FINANCIAL_RESEARCH_ARCHITECTURE_20260920.md`、Grok 平台、单票因子和决策记忆三份研究稿。结论针对“弱模型、24/7、多 Agent、手机使用、三类投资研究、深度主观来源和历史复盘”的第一版，不评估尚未找到的 `sec-analysis` 实现。

## 总判断

方向基本正确：Grok Bot 适合做常驻入口、任务分派和材料组织；证据、计算、判断版本和失败状态必须由确定性系统控制。当前草案最大的问题不是缺更多 Agent，而是仍把“共享云电脑 + Routine + 单写 SQLite”写得太接近生产底座。官方只承诺后台运行和共享电脑，不提供调度 SLA；Routine 甚至可能在用户长期离开后被暂停，手机推送也仍在逐步开放。

因此应把第一版明确改成两层：

```text
手机单一入口（Chief）
  -> 专员任务（按需调用，不长期自治）
  -> research-core（队列、取数、去重、估值、因子、门禁、账本、回执）
  -> Reviewer 读取同一 evidence packet 后独立退回/放行
```

Grok Bot 可持续工作，但不能单独承诺“无人值守 24/7 决策服务”。PoC 若暂不部署外部 `research-core`，应明确标为可中断实验系统，不宣传告警 SLA。

## P0：实施前必须修改

### 1. 把可靠状态机移出 Agent 对话和共享文件约定

当前的 `queued → running → ...`、租约和幂等设计是对的，但“数据管家是唯一写入者”只是提示词规则。所有 Bot 共用同一电脑、文件、登录和命令行凭据，角色不是权限边界；任一 Bot 都可能误写 SQLite、覆盖文件或重复发布。

改为一个窄接口的 `research-core`：Bot 只能 `submit_task`、`append_evidence`、`get_packet`、`propose_decision`，不能直接打开主库。服务端生成业务幂等键，做 schema、时点、引用、版本和状态迁移校验。PoC 可先在云电脑跑本地服务，但 P4 常态运行前应放到独立持久服务，并做每日备份和恢复演练。

每次运行最低契约应含：`run_id`、对象、工作流、`decision_cutoff`、输入 snapshot、尝试号、租约、预算、状态、错误类别、输出 hash、通知状态。只有 `published` 产物可被 Chief 读取；`completed` 不等于已发布。

### 2. 24/7 和移动提醒必须有独立健康证明

官方文档确认笔记本关闭后 Bot/Routine 仍可运行，但 Routine 可能因长期无人响应而暂停，每个 Routine 只保留最近 20 次记录；移动 push 还未对所有账户完全开放。这意味着“任务是否准时发生”和“用户是否收到异常”都不能由同一 Routine 自证。

第一阶段增加独立 `expected-run` 表：预先产生应运行的交易日实例，完成后写 receipt；另一个不依赖该业务 Routine 的心跳检查缺口。关键告警至少经过一个已实测的第二通道。手机端保留单一 Chief 会话，只推送“改判、硬阻塞、证据到期和用户需要处理”，专员 chatter 不直接通知用户。

### 3. 在定义投资政策前，禁止正式 BUY/SELL

草案把市场、周期、风险约束和预算留为“实施前再确认参数”，但它们直接决定行动语义。没有持有期、基础币种、税费、现金、成本基础、最大仓位/亏损、流动性和组合暴露，系统无法区分“公司便宜”与“账户应该买”。

在 `investment_policy_version` 建立前，只允许输出 `WATCH` 或 `ABSTAIN`。之后严格分三层：

1. `company_thesis`：业务论点是否成立；
2. `security_value`：在给定期限和回报要求下的价值区间；
3. `portfolio_action`：结合真实持仓、敞口和事件窗口给 `BUY/SELL/WATCH`。

`SELL` 只对真实持仓使用；观察名单的负面结论仍是 `WATCH`，并注明“不进入/移出关注”。券商快照过期时可以更新研究结论，但不得更新仓位动作。

### 4. 明确弱模型不能决定数值和最终状态迁移

Chief 可以起草解释、提出缺口和比较已通过门禁的选项，不能自行算目标价、改变 evidence 状态、把 rumor 升级为 fact、覆盖 Reviewer 退回，或把失败任务标成完成。

最终标签应由确定性合成器根据已批准论点状态、估值输入、报价新鲜度、组合约束和因子状态产生；模型只能对未结构化材料给出带证据 ID 的候选判断。重大分歧保留在卡片上，不能通过“多 Bot 投票”消失。

## P1：补齐研究质量

### 5. “理想价位”需拆成价值区间和执行区间

当前文本说用情景估值和安全边际推导区间，但没有规定多种证据如何合成。建议每票固定输出：

- `fair_value_range`：bear/base/bull 的经营假设、估值方法、期限和敏感性；
- `entry_ceiling`：按用户要求回报和安全边际反推的最高买入价；
- `trim/exit_band`：估值过高或论点破坏时的减仓/退出条件；
- `execution_state`：价格行为只影响分批、等待或加速，不改写基本面公允价值。

投行目标价、内部 DCF/倍数法和技术位不得平均。它们应并列，解释期限、盈利口径、股本、币种和分歧来源。缺失关键输入时不显示精确价位。

### 6. 单票因子门禁过于精确，且与“辅助主观决策”的效用没有完全对齐

`7 年/1,750 日`、`756 日 OOS`、`2/3 折同向`、`单状态不超过 70%`、`90% bootstrap 下界 > 0` 等适合作为初始实验协议，不应写成跨股票的永久真理。60 日重叠标签的有效样本远少于交易日数，结构突变又可能让更长历史降低当前相关性。DSR 也不能修复未完整记录的人工试验或错误的试验相关性假设。

改成分层证据：`descriptive → exploratory → promoted → prospective-confirmed`。每个研究先注册决策问题、预测期限、基准、成本、候选数和主要指标，再由有效样本量、标签重叠和状态覆盖决定门槛。硬性要求保留 PIT、无泄漏、所有试验留痕、按块重采样、成本压力和前瞻 shadow 期；数值阈值进入可版本化 protocol，不写死在平台总规。

评估也需增加“相对主观基线的增量”：覆盖率/弃权率、方向或概率校准、入场改善、避免回撤、换手与最差状态。不能只用策略超额收益判断因子是否帮助了用户。

### 7. 价格行为必须是受限的时机层

建议使用预先注册的少量趋势、反转、波动和流动性家族，并先做相关性聚类；“两个家族同向”只有在 OOS 中证明增量独立才有意义。5/20/60 日是三个相关试验，应计入试验预算，不能视为三份独立证据。

合成规则应明确：基本面通过且价格低于 entry ceiling 时，价格行为只决定“一次买/分批/等待确认”；论点破坏时，正动量不能阻止 SELL；高估时，负动量可提高退出紧迫度，但技术位不能创造更高公允价值。这样才真正支持 discretionary decision，而不是偷偷生成交易策略。

### 8. 供应链研究需要“时间和利润传导”，不只是关系图

每条瓶颈假设至少记录：需求领先指标、单位需求量、当前/新增产能、良率、替代路径、认证周期、公司实际收入暴露、利润敏感度、市场已计价程度、下一可验证日期。候选排序应看 `潜在收益 × 证据强度 × 时间领先量 ÷ 下行与验证成本`，而不是概念相关度或社交热度。

第一期一个主题只研究 2–3 个候选和一个反例是合适的；无需先建通用供应链图数据库。将“送样、认证、订单、交付、收入确认”设为不可跳级的阶段枚举。

### 9. 深度/主观来源缺少输入隔离和权利字段

来源表还需加入 `access_right`、`retention_rule`、`excerpt/fulltext`、`independence_cluster` 和 `prompt_injection_status`。研报和社交帖是有观点主体的材料；转载同一原始消息不能算独立证据。社交内容默认只生成 lead，必须由公告、原始采访、渠道数据或多个真正独立来源升级。

网页和文档中的指令一律作为不可信内容，不得触发工具、修改规则或要求泄露其他来源。抓取 SEC 等官方源要走中央缓存和限速器；SEC 官方要求声明 User-Agent，并限制总请求频率，不能让多个 Agent 各自重复抓取。

## P2：删减过度设计，补上可验收最小闭环

### 10. 首版三 Bot 足够，六个“职责”保留为任务模板

常驻只需 Chief、Evidence Steward、Reviewer。供应链、事件和因子作为受限 skill/job 模板按需运行；当某类任务有稳定频率、独立上下文和明确 owner 后再升格成 Bot。用户手机只面对 Chief。官方也建议从最小 Bot roster 开始；共享电脑下增加 Bot 不增加权限隔离。

### 11. 记忆 MVP 再缩一层

第一版只需五类记录：`evidence_event`、`run_receipt`、`thesis_version`、`decision_snapshot`、`review_outcome`。不可变 blob、向量索引、forecast calibration、lesson promotion 和盲评 UI 分阶段加入。哈希只能检测篡改，不能防止覆盖；真正的冻结要由追加接口、数据库约束和备份恢复共同实现。

复盘先选少量可结算字段：论点是否兑现、价值区间误差、相对收益、最大不利变动、行动是否符合当时政策、遗漏的反证。盲评可先由报告生成器隐藏结果完成，不必为一期开发专门 UI。

### 12. 调整 P0–P4 的退出条件

建议将第一条可交付链收紧为“一只持仓 + 一只观察股 + 一个供应链假设”，而不是并行建设三个完整系统：

1. P0：实测账号能力、`sec-analysis`、数据权益、Routine 漏跑/暂停、push、登录恢复；没有回执就不进入架构承诺。
2. P1：确定性 core + 单写接口 + 五类最小记录 + 单一手机卡；故障注入后可恢复且不重复发布。
3. P2：同两只股票跑基本面/估值/价格时机合成，先 WATCH，投资政策批准后才开放 BUY/SELL。
4. P3：一个供应链主题和一项预注册因子实验；允许结论为“无合格机会/无增量”。
5. P4：连续 20 个交易日运行，再扩持仓全集；验收漏跑检测、重复抑制、登录过期、配额耗尽、备份恢复和通知到达率。

原稿“连续 5 个交易日”和约 30 个案例适合作为 PoC 冒烟，不足以证明常态运行。生产候选至少要覆盖一个月、一次计划内故障和一次人工恢复。

## 已核实的关键产品边界

- Grok Bot 官方确认所有 Bot 共用同一台云电脑、文件和登录；每 Bot 有独立屏幕，但同一屏幕一次只跑一个 computer-use 任务。这支持并行研究，不支持把 Bot 当安全边界：[Overview](https://docs.x.ai/grok-bot/overview)。
- 官方 Routine 文档确认每 Bot 最多 50 个 Routine、每个仅保留最近 20 次记录，并可能在用户长期离开后询问是否继续、无响应则暂停：[Skills and routines](https://docs.x.ai/grok-bot/skills-routines-and-automations)。
- 官方移动端文档确认 push 仍在逐步开放，且编辑/测试 Routine 目前需要桌面端：[Mobile](https://docs.x.ai/grok-bot/mobile)。
- 官方设置文档确认没有模型选择器，因此不能通过给各 Bot 指定强模型来补可靠性：[Settings](https://docs.x.ai/grok-bot/settings-and-notifications)。
- SEC 官方要求自动访问声明 User-Agent，并将总请求频率限制在每秒 10 次；多 Agent 必须共享缓存和速率预算：[Accessing EDGAR Data](https://www.sec.gov/search-filings/edgar-search-assistance/accessing-edgar-data)。

## 保留不改的部分

原稿以下判断应保留：不自动下单；价格/持仓/证据都带时点；缺数据时正常 `ABSTAIN`；主观来源与事实分层；供应链必须从瓶颈走到利润和估值；单票不用横截面 Rank IC；失败实验和旧判断不被删除；Routine 先手工跑通再自动化；最终允许得出“无机会/无稳定因子”的结论。
